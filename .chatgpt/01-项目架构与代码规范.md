# Flutter Deer 项目架构与代码规范

> 本文根据当前仓库源码、目录结构、`pubspec.yaml`、测试目录及 `README.md` 整理。
> 目标是说明“代码应该放在哪里、各包负责什么、模块之间如何协作”。如果后续代码与本文不一致，应先判断是文档需要更新，还是代码放置不符合约定。

## 1. 项目定位与总体结构

这是一个单 Flutter 应用，Dart 包名为 `flutter_deer`，业务定位为店铺管理类练习项目。项目没有拆分为多个 Dart/Flutter package，所有应用代码都位于 `lib/`，通过顶层目录区分业务域和公共能力。

总体上采用：

```text
应用启动与全局配置
        ↓
全局路由（routers）
        ↓
业务模块（home / login / shop / goods / order / store / account / setting / statistics）
        ↓
页面、状态、模型、业务组件
        ↓
公共基础能力（net / mvp / res / util / widgets）
```

需要注意：项目不是严格的单一架构实现，而是两种状态组织方式并存：

- 大多数页面直接使用 `provider` + `ChangeNotifier` 管理局部或全局状态。
- `shop`、`order` 的部分页面仍使用 `mvp` 中的 `BasePageMixin`、`BasePagePresenter`；`order_search_page.dart` 还通过 `PowerPresenter` 组合多个 Presenter。

因此新增功能应优先沿用所在业务模块已有的方式，不要在同一个功能链路中无理由混用两套状态方案。

## 3. `lib` 顶层包分类

### 3.1 应用入口

| 包 | 主要文件 | 职责 |
| --- | --- | --- |
| `lib/main.dart` | `main.dart` | Flutter 入口、异常处理、桌面窗口初始化、URL 策略、持久化初始化、Dio 配置、全局 Provider、MaterialApp 配置 |

`main.dart` 中的 `MyApp` 会完成全局初始化，并注入 `ThemeProvider`、`LocaleProvider`。应用默认入口是 `home/splash_page.dart`，路由生成器来自 `routers/routers.dart`。

### 3.2 业务模块

业务模块一般使用以下内部分类：

```text
lib/<业务模块>/
├── <业务模块>_router.dart   # 本模块路由及路径常量
├── page/                    # 页面级 Widget，文件名以 *_page.dart 结尾
├── models/                  # 本模块实体、模型、数据结构
├── provider/                # provider 状态对象，通常继承 ChangeNotifier
├── presenter/               # MVP Presenter；仅在采用 MVP 的模块中出现
├── iview/                   # MVP View 接口；仅在采用 MVP 的模块中出现
└── widgets/                 # 仅服务本模块的可复用 Widget、Dialog、BottomSheet 等
```

当前业务包如下：

| 包名 | 业务职责 | 当前子包/代表文件 |
| --- | --- | --- |
| `home` | 启动页、首页容器、底部主导航、WebView | `splash_page.dart`、`home_page.dart`、`webview_page.dart`、`provider/home_provider.dart` |
| `login` | 登录、注册、短信登录、密码重置/修改 | `page/`、`widgets/my_text_field.dart`、`login_router.dart` |
| `shop` | 店铺主页、店铺设置、配送/地址/消息等 | `page/`、`provider/user_provider.dart`、`presenter/shop_presenter.dart`、`iview/shop_iview.dart`、`models/`、`widgets/` |
| `goods` | 商品、商品分类、规格、搜索、扫码和编辑 | `page/`、`provider/`、`models/`、`widgets/`、`goods_router.dart` |
| `order` | 订单列表、详情、搜索、物流跟踪 | `page/`、`provider/`、`presenter/`、`iview/`、`models/`、`widgets/` |
| `store` | 店铺审核及审核结果 | `page/`、`store_router.dart` |
| `account` | 账户、银行卡、提现、城市选择及账户记录 | `page/`、`models/`、`widgets/`、`account_router.dart` |
| `setting` | 设置、主题、语言、账户管理、关于 | `page/`、`provider/`、`widgets/`、`setting_router.dart` |
| `statistics` | 商品统计、订单统计 | `page/`、`widgets/`、`statistics_router.dart` |

新增业务功能的归属判断：先按业务领域归入上述模块；只有无法归入现有领域且确实是新的业务边界时，才新增 `lib/<new_module>/`，并补充自己的路由文件。

### 3.3 公共基础包

| 包名 | 职责 | 放置规则 |
| --- | --- | --- |
| `routers` | 全局 Fluro 路由、路由接口、导航工具、未找到页面、转场 | 跨业务路由基础设施放这里；具体业务路径仍放业务模块的 `*_router.dart` |
| `net` | Dio 网络请求封装、请求方法、错误处理、拦截器、接口地址、基础响应实体 | 与具体业务页面无关的网络基础设施放这里；业务请求调用方仍放在对应 Provider/Presenter 中 |
| `mvp` | MVP 生命周期、View 接口、Presenter 基类、网络请求 Presenter、Presenter 组合器 | 仅放通用 MVP 框架代码，不放某个业务的具体 Presenter |
| `res` | 颜色、尺寸、间距、样式、常量、资源统一出口 | 全局设计常量和资源入口放这里；业务专属资源仍按 `assets/images/<module>/` 管理 |
| `util` | 设备、日期、主题、图片、日志、Toast、版本、导航、输入格式化等工具 | 无明确业务归属且可被多个模块复用的纯工具放这里；有业务含义的逻辑不要随意塞进 `util` |
| `widgets` | 全局可复用 Widget、Dialog、列表/刷新/状态布局、图表组件等 | 至少被多个业务模块使用，或明确属于通用 UI 基础设施时放这里；只服务单一业务的 Widget 放业务模块内部 |

### 3.4 特殊代码包

| 包名 | 职责 | 规则 |
| --- | --- | --- |
| `generated/json` | JSON Bean 转换生成代码及其基础转换器 | `*.g.dart` 为生成文件，不手工修改；源实体放回对应业务模块的 `models/` |
| `l10n` | 本地化 ARB、生成的本地化 Dart 文件 | `intl_*.arb` 是翻译源文件；生成 Dart 文件由 Flutter 本地化生成流程维护 |
| `demo` | 动画、Focus、Lottie、刮刮卡、Overlay、Navigator 等独立演示代码 | 仅用于学习/演示的代码放这里，不应被正式业务模块依赖；入口由 `demo/demo_page.dart` 汇总 |

## 4. 路由架构与页面进入规则

项目使用 `fluro`。路由职责分为三层：

1. `routers/i_router.dart` 定义 `IRouterProvider` 接口，要求模块提供 `initRouter(FluroRouter router)`。
2. 每个业务模块通过 `<module>/<module>_router.dart` 实现接口，并维护本模块路径常量和页面 Handler。
3. `routers/routers.dart` 负责初始化全局路由，并把各业务 Router 加入 `_listRouter`。

当前初始化顺序包含：`ShopRouter`、`LoginRouter`、`GoodsRouter`、`OrderRouter`、`StoreRouter`、`AccountRouter`、`SettingRouter`、`StatisticsRouter`；首页和 WebView 路由由全局 `Routes` 直接定义。

新增页面时应：

1. 页面放入所属模块的 `page/`，命名为 `<meaning>_page.dart`。
2. 在所属模块的 `*_router.dart` 增加路径常量和 Handler。
3. 只有新增业务模块时，才在全局 `routers/routers.dart` 注册新的 Router。
4. 页面跳转优先使用现有 `routers/fluro_navigator.dart` 封装，不在业务页面重复封装导航逻辑。
5. 路由参数要在 Router Handler 中完成解析、解码和类型转换，页面接收明确类型的构造参数。

## 5. 状态管理与业务逻辑

### Provider 路径

`provider/` 下的类通常继承 `ChangeNotifier`，由页面附近的 `ChangeNotifierProvider` 创建，再通过 `Consumer` 或 Provider API 读取状态。当前代表包括：

- 全局：`setting/provider/theme_provider.dart`、`locale_provider.dart`，在 `main.dart` 注入。
- 页面/模块：`home/provider/home_provider.dart`、`goods/provider/goods_page_provider.dart`、`goods_sort_provider.dart`、`order/provider/order_page_provider.dart`、`shop/provider/user_provider.dart`。
- 通用列表：`order/provider/base_list_provider.dart`。

新增 Provider 应只负责状态、状态变更和与页面相关的协调逻辑；Widget 不要承载大段数据处理。Provider 的生命周期要与页面一致，使用 `.value` 时要明确谁负责销毁。

### MVP 路径

`mvp/` 提供 `BasePageMixin`、`BasePresenter`、`BasePagePresenter`、`PowerPresenter` 和 View 生命周期接口。当前主要应用在：

- `shop/page/shop_page.dart` + `shop/presenter/shop_presenter.dart` + `shop/iview/shop_iview.dart`
- `order/page/order_search_page.dart` + `order/presenter/order_search_presenter.dart`，并组合 `ShopPagePresenter`

新增 MVP 页面应将具体 Presenter 放到本模块 `presenter/`，View 接口放到本模块 `iview/`，页面通过 `BasePageMixin` 绑定；网络请求应使用 `BasePagePresenter` 的请求能力，以便统一处理加载框、取消请求和错误提示。

## 6. 网络与数据模型规范

- `net/dio_utils.dart` 是网络请求入口，`http_api.dart` 集中接口地址，`intercept.dart` 放认证、Token、日志、数据适配等拦截器。
- `net/base_entity.dart` 放通用响应结构；业务实体放到具体模块的 `models/`。
- JSON 生成文件统一放 `generated/json/`，文件名以实体名对应的 `*.g.dart` 结尾。不要直接编辑生成文件。
- 页面不应直接散落 Dio 配置、拦截器和基础错误处理；请求协调放 Provider 或 Presenter，网络基础能力放 `net/`。
- 当前 `main.dart` 中配置了 GitHub API 基础地址，若接入真实后端，应将环境差异和基础地址集中管理，避免在页面中硬编码。

## 7. 命名与文件放置约定

源码当前整体采用 Dart 常见的 `lower_snake_case` 文件名和目录名，类名采用 `UpperCamelCase`。新增代码遵循以下规则：

| 类型 | 命名示例 | 放置位置 |
| --- | --- | --- |
| 页面 | `goods_edit_page.dart` / `GoodsEditPage` | `lib/<module>/page/` |
| 页面局部组件 | `goods_item.dart` / `GoodsItem` | `lib/<module>/widgets/` |
| 公共组件 | `my_button.dart` / `MyButton` | `lib/widgets/` |
| Provider | `goods_page_provider.dart` / `GoodsPageProvider` | `lib/<module>/provider/` |
| Presenter | `shop_presenter.dart` / `ShopPagePresenter` | `lib/<module>/presenter/` |
| View 接口 | `shop_iview.dart` / `ShopIMvpView` | `lib/<module>/iview/` |
| 模型/实体 | `user_entity.dart` / `UserEntity` | `lib/<module>/models/` |
| 路由 | `goods_router.dart` / `GoodsRouter` | `lib/<module>/` |
| 工具 | `theme_utils.dart` / `ThemeUtils` | `lib/util/` |
| 常量/资源 | `colors.dart`、`dimens.dart`、`resources.dart` | `lib/res/` |

文件命名尽量体现职责，避免使用含义不清的 `common.dart`、`manager.dart`、`helper.dart`。如果文件仅供某一个模块使用，不要因为“以后可能复用”提前放入全局包。

## 8. import 与依赖方向

推荐依赖方向如下：

```text
页面/业务 Widget
  ├── 本模块 provider / presenter / models / widgets
  ├── routers / res / util / widgets
  └── net（通常经 Provider/Presenter 间接使用）

公共基础包（res / util / widgets / net / mvp）
  └── 不应依赖具体业务模块
```

约束：

- 优先使用 `package:flutter_deer/...` 绝对导入，保持与现有代码一致。
- 业务模块之间尽量通过路由或公共模型交互，不要形成环形 import。
- `widgets/`、`util/`、`net/`、`mvp/` 不应反向依赖 `goods`、`order` 等具体业务包。
- 业务专属组件放业务包内；当组件确实被多个模块使用后，再移动到公共 `widgets/`，并同步修改 import。
- 资源访问优先经过 `res/resources.dart` 或现有资源常量，不在页面中重复拼接资源路径。

## 9. 资源、本地化与测试

### 资源

`assets/images/` 已按 `home/store/state/order/login/goods/shop/account/statistic` 等业务目录组织，新增业务图片优先放入对应目录，并在 `pubspec.yaml` 添加资源目录声明。Lottie 文件放 `assets/lottie/`，数据文件放 `assets/data/`。

### 本地化

翻译源文件位于 `lib/l10n/intl_zh.arb` 和 `lib/l10n/intl_en.arb`，`l10n.yaml` 控制生成配置。新增文案应优先补充 ARB，不要在页面中散落硬编码的用户可见文本；生成文件不要手改。

### 测试

- `test/`：按业务模块组织可访问性测试，如 `test/goods/goods_accessibility_test.dart`；通用网络测试放 `test/net/`。
- `integration_test/`：放集成测试流程及入口。
- `test_driver/`：按业务模块组织驱动脚本和测试入口，与集成测试保持可追溯关系。
- 新增业务页面至少应考虑 Widget/可访问性测试；涉及跨页面流程时补充集成测试或 driver 测试。

## 10. 新功能落地清单

1. 先确定业务归属；归入现有模块，不直接在 `lib/` 根目录新增文件。
2. 页面放 `page/`，页面专属组件放 `widgets/`。
3. 需要状态时放 `provider/`；若模块已有 MVP 链路且该功能属于同一链路，则放 `presenter/` 和 `iview/`。
4. 数据对象放 `models/`，生成转换代码交给 `generated/json/`。
5. 在模块 `*_router.dart` 注册页面，并在 Handler 中解析参数。
6. 复用已有 `res`、`util`、公共 `widgets` 和 `routers` 能力，避免重复实现。
7. 新资源登记到 `pubspec.yaml`，新文案登记到 ARB。
8. 补充对应测试，并执行静态分析和相关测试。
9. 如果新建了业务模块，再把其 Router 加入 `routers/routers.dart`。
10. 本次新增了新的目录分类或架构约定时，同步更新本文档。

## 11. 当前结构的边界与维护提醒

- `provider` 与 MVP 并存是当前事实，不建议为了追求形式统一而一次性迁移全项目。
- `demo` 是演示/学习代码，和正式业务模块的页面、状态、路由规则不同，应保持隔离。
- `generated`、平台插件注册文件和构建产物属于工具生成或平台生成内容，除非任务明确涉及，不要手工重构。
- `README.md` 中的部分版本描述可能随仓库演进而变化；依赖和 SDK 约束以当前 `pubspec.yaml`、锁定文件和实际构建结果为准。
- 本文档记录的是当前源码结构和推荐放置规则，不替代 Dart/Flutter 官方 lint 规则；具体语法和静态检查以 `analysis_options.yaml` 为准。
